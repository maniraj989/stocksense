# StockSense — PostgreSQL Migration Notes & Design Decisions

This document details the conversion rules applied from the legacy MySQL 8 schema to modern PostgreSQL 16+ for Flyway baseline migration (`V1__initial_postgresql_schema.sql`).

---

## 1. Syntax & Data Type Conversions

| MySQL Construct | PostgreSQL Target | Rationale |
| :--- | :--- | :--- |
| `INT PRIMARY KEY AUTO_INCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Standard SQL compliance; supports high-volume scalability and avoids sequence desynchronization. |
| `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | `TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP` | Timezone-aware timestamp prevents ambiguities across daylight savings and server regions. |
| `DATE` | `DATE` | Maintained for calendar-only dates such as product expiry. |
| `DECIMAL(10,2)` / `DECIMAL(12,2)` | `NUMERIC(19,4)` | Enterprise financial precision prevents floating-point inaccuracies and rounding drift during subtotal/tax calculations. |
| `ENUM('ADMIN', 'STAFF')` | `VARCHAR(50) CHECK (role IN ('ADMIN', 'STAFF'))` | Check constraints provide superior migration flexibility compared to native database enum types (which complicate DDL alterations in PostgreSQL). |
| `ENUM('IN', 'OUT', 'ADJUSTMENT')` | `VARCHAR(50) CHECK (movement_type IN ('IN', 'OUT', 'ADJUSTMENT'))` | Extensible constraint architecture for subsequent migrations. |
| `ENUM('LOW_STOCK', 'EXPIRY', 'REORDER')` | `VARCHAR(50) CHECK (alert_type IN ('LOW_STOCK', 'EXPIRY', 'REORDER'))` | Check constraints allow easy expansion without locking tables. |
| `TEXT` | `TEXT` | Native PostgreSQL variable-length character string. |
| `ON UPDATE CURRENT_TIMESTAMP` | PostgreSQL Trigger / ORM `@UpdateTimestamp` | PostgreSQL does not have inline `ON UPDATE CURRENT_TIMESTAMP`; handled via standard trigger or application-level timestamps. |

## 2. Foreign Key & Constraint Integrity

All 9 foreign key relationships and deletion rules from the original schema are strictly preserved:

1. `fk_products_supplier`: `products(supplier_id)` $\to$ `suppliers(id)` `ON DELETE SET NULL`
2. `fk_purchases_supplier`: `purchases(supplier_id)` $\to$ `suppliers(id)` `ON DELETE RESTRICT`
3. `fk_purchases_user`: `purchases(created_by)` $\to$ `users(id)` `ON DELETE SET NULL`
4. `fk_purchase_items_purchase`: `purchase_items(purchase_id)` $\to$ `purchases(id)` `ON DELETE CASCADE`
5. `fk_purchase_items_product`: `purchase_items(product_id)` $\to$ `products(id)` `ON DELETE RESTRICT`
6. `fk_sales_user`: `sales(created_by)` $\to$ `users(id)` `ON DELETE SET NULL`
7. `fk_sale_items_sale`: `sale_items(sale_id)` $\to$ `sales(id)` `ON DELETE CASCADE`
8. `fk_sale_items_product`: `sale_items(product_id)` $\to$ `products(id)` `ON DELETE RESTRICT`
9. `fk_stock_movements_product`: `stock_movements(product_id)` $\to$ `products(id)` `ON DELETE CASCADE`
10. `fk_stock_movements_user`: `stock_movements(created_by)` $\to$ `users(id)` `ON DELETE SET NULL`
11. `fk_alerts_product`: `alerts(product_id)` $\to$ `products(id)` `ON DELETE CASCADE`

## 3. Explicit Index Strategy in V1

To optimize queries identified in `ProductDAO`, `SaleDAO`, `PurchaseDAO`, and `StockMovementDAO`:

* `idx_users_username`: Fast user lookup during authentication
* `idx_products_product_code`: Barcode / SKU lookup
* `idx_products_supplier_id`: Join acceleration with suppliers
* `idx_products_category`: Product filtering
* `idx_products_quantity_min`: Low stock detection (`quantity <= minimum_stock`)
* `idx_products_expiry_date`: Expiry date window searches
* `idx_purchases_supplier_id`: Supplier purchase history
* `idx_purchases_date`: Date range purchase aggregation
* `idx_sales_date`: Revenue and sales aggregation queries
* `idx_stock_movements_product_id`: Stock history queries
* `idx_alerts_product_status`: Alert filtering by status and product
